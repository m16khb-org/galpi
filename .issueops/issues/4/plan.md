## 목표와 비목표

**목표 (이슈 완료 기준 8개를 그대로 만족)**

1. 설정 시트에 "ChatGPT로 계속하기" 버튼을 두고, 누르면 시스템 브라우저가 `auth.openai.com`으로 열리며, 승인 뒤 "`<이메일>`로 로그인됨"을 표시한다.
2. 앱을 재시작해도 로그인 상태가 유지되고, 토큰 값은 IPC로 프런트엔드에 넘어가지 않는다(저장 여부·이메일만 전달).
3. 로그인 상태에서 모델 선택 목록이 계정의 `GET /v1/models`(`visibility == "list"`) 결과로 채워지고, 선택한 `slug`가 정제 요청의 `model`로 전달된다.
4. ChatGPT 모드의 회의록 정제가 `POST /v1/responses` 스트림(`store:false`, `stream:true`, `instructions`)으로 `response.completed`까지 읽혀 `_회의록.md`를 만들고, 긴 회의의 맵·리듀스 경로도 같은 전송을 쓴다.
5. access token 만료 뒤 정제를 실행하면 refresh token으로 자동 갱신한 뒤 성공하고, 교체된 refresh token이 저장소에 교체 저장된다.
6. 로그아웃하면 저장소의 토큰과 발급 `client_id`가 지워지고 API 키 모드로 돌아가며 `ext_agent_host_id`는 유지된다.
7. 사용량 한도 초과(`subscription_sharing_usage_limit_exceeded`)와 동의 거부(`access_denied`)가 한국어 상태 문구로 표시되고 앱이 재전송하지 않는다.
8. API 키 모드의 기존 테스트(`refinement_sends_saved_background_and_publishes_minutes` 등)가 수정 없이 통과한다.

**결정 사항 (이슈의 "열린 결정" 해소)**

- `ext_agent_host_id`는 `urn:uuid:<UUIDv4>`로 한다. 공식 문서는 JWK thumbprint를 "권장하되 선택", UUID를 "지원되는 대안"으로 적고, "공개키 소유를 OpenAI가 검증하지 않는다"고 명시한다. thumbprint를 쓰려면 키 쌍을 만들고 비밀키를 별도 저장해야 하는데 현재는 보안상 이득이 없다. 값은 불투명 문자열이라 나중에 바꿔도 저장값 교체뿐이다.
- 기본 모델은 서버가 준 목록 순서를 그대로 쓰고, 저장된 선택이 없거나 목록에 더는 없으면 첫 항목을 고른다. 공식 문서가 "서버 순서 보존"을 요구한다.

**비목표**: 웹사이트형 SIWC(client secret), Codex app-server 연동, Codex CLI의 비공개 OAuth client, `chatgpt.com/backend-api` 경로, OpenAI 외 제공자 OAuth, 다른 소셜 로그인, ASR을 GPT로 바꾸는 일(공식 문서: 오디오 입력·transcription API 미지원), 다중 ChatGPT 계정 선택기(공식 문서는 선택 사항이며 이슈 범위 밖), OpenAI 로고 에셋 포함(미확인 가정: 승인 에셋의 배포 조건은 이 계획에서 확인하지 않았으므로 텍스트 버튼만 쓴다).

## 이슈 본문과 다른 사실

1. **현재 비밀 저장소는 Keychain이 아니라 0600 설정 파일이다.** `src-tauri/src/adapters/outbound/secrets.rs:1-9`("it is not what the app uses yet … secrets stay in the settings file"), `src-tauri/src/adapters/outbound/settings.rs:39-41`(`secrets: Arc::new(SettingsFile)`), `README.md:162-163`가 이를 확인한다. 커밋 `e283101`이 ad-hoc 서명 때문에 Keychain을 되돌렸다. 따라서 완료 기준 5·6의 "keychain에 교체 저장", 검증의 `security find-generic-password -s galpi`는 그대로는 성립하지 않는다(서비스명도 `galpi`가 아니라 `com.m16khb.galpi`, `secrets.rs:15`). 이 계획은 "keychain"을 "현재 `SecretStore` 구현(= 설정 파일 0600, Developer ID 서명 후 `Keychain`으로 교체되는 같은 경로)"으로 읽고, 게이트에서는 `settings.json` 키 검사로 대체한다. `security` 명령은 현재 구현에서 항상 비어 있어 공허하므로 게이트로 쓰지 않는다.
2. **"`ports.rs`의 비밀 저장 포트"는 없다.** `SecretStore` trait은 어댑터 소유(`secrets.rs:45-55`)이고, `ports.rs:86-100`의 `SettingsPort`는 비밀별 메서드(`load_assistant_api_key` 등)만 노출한다. 새 ChatGPT 저장은 `SettingsPort`를 부풀리지 않고 새 `ChatGptStore` 포트로 두되, 같은 `LocalSettingsStore`가 구현한다(같은 `settings.json`을 두 객체가 쓰면 경쟁하므로).
3. **공식 문서와 이슈의 로그아웃 정의가 다르다.** 공식 문서(`profiles-and-sessions`)는 로그아웃 시 "account/client mapping과 host ID를 유지"하라고 하고, 이슈 완료 기준 6은 "발급 `client_id`가 지워진다"고 한다. 이슈 본문이 계약이므로 이슈를 따른다. 결과: 로그아웃 뒤 재로그인은 새 동적 등록이 되어 ChatGPT 설정에 앱 등록이 하나 더 생길 수 있다. 위험 절에 기록한다. 로그아웃 때 공식 문서의 `revocation_endpoint` 폐기 시도는 이슈에 없지만 문서가 요구하므로 포함한다(이슈 비충돌).

**새로 만드는 것과 정당화**

- **`AssistantSettings`(Rust·TS)는 수정하지 않는다.** 이 문서는 autosave로 창에서 통째로 되돌아오는 값(`save_assistant`, `settings.rs:312-325`)인데, 로그인 상태처럼 *호스트가 소유한* 값을 여기에 넣으면 `fdd8caf`가 고친 "창이 오래된 호스트 값을 되돌려 지우는" 사고를 재현할 수 있다. 그래서 창이 소유하는 선택(`authMode`, `model`)과 호스트가 소유하는 상태(계정)를 별도 값 객체 `ChatGptSettings`/`ChatGptPreferences`와 별도 커맨드로 둔다. 부수 효과로 API 키 모드의 계약과 테스트 픽스처(Rust의 `AssistantSettings { .. }` 구조체 리터럴 — `application/tests.rs:407,534,649`, `settings.rs` 테스트, `roster.rs` 테스트 — 과 TS의 `apiKeyStored` 리터럴 — `assistant-settings.dom.test.ts`, `controller.test.ts`, `settings-autosave.dom.test.ts`)이 한 줄도 바뀌지 않는다. 필드를 추가하면 이 리터럴이 전부 컴파일되지 않는다. 롤백도 쉽다.
- **새 의존성**(현재 HTTP 클라이언트·JWT·난수 크레이트가 직접 의존성에 없음 — `Cargo.toml:16-30` 확인. `Cargo.lock`의 `reqwest 0.13.4`는 `tauri`의 전이 의존성이며 TLS 크레이트가 하나도 없어(`rustls`·`native-tls`·`openssl` 없음) HTTPS에는 쓸 수 없다):
  - `reqwest = { version = "0.13", default-features = false, features = ["native-tls", "form"] }` — macOS에서 `native-tls`는 Security.framework를 쓰므로 이미 직접 의존성인 `security-framework 3.7.0`과 같은 계열이고 C 툴체인(aws-lc/cmake)이 필요 없다. 기본 TLS(rustls + aws-lc-rs)는 CI·ARM64 빌드에 C 컴파일을 끌어들여 기각한다. `json` feature는 쓰지 않고 `serde_json::from_slice`로 파싱한다.
  - `jsonwebtoken` 11 (default-features 끔, `rust_crypto` 기능만) — ID 토큰 RS256 검증은 직접 구현하지 말고 유지되는 라이브러리를 쓰라는 공식 문서 권고를 따른다(`aws_lc_rs` 백엔드는 위와 같은 이유로 기각). JWKS의 `n`/`e`를 `DecodingKey::from_rsa_components`에 그대로 넣는다. discovery 문서가 `id_token_signing_alg_values_supported: ["RS256"]`만 광고한다.
  - `base64 = "0.22"`, `sha2 = "0.10"`(둘 다 이미 lock에 있음)과 `getrandom = "0.4"`(lock에 있음) — PKCE(S256)·state·nonce 난수. `uuid`에 `v4` feature 추가(`ext_agent_host_id`).
  - `tokio`에 `net` feature 추가(loopback 리스너). 별도 HTTP 서버 크레이트는 쓰지 않는다 — 요청줄·헤더 8 KiB·쿼리 파싱 60줄 안팎이면 충분하고, 노출 면이 작다.
  - dev-dependency로 `rsa`(테스트용 RS256 키 쌍을 `OnceLock`으로 한 번만 생성; 비밀키 PEM을 저장소에 커밋하지 않기 위함 — 비밀 스캐너·CONSTITUTION 때문).
  - 구현 첫 단계에서 `cargo check`로 feature 이름·API를 확인한다. `DecodingKey::from_rsa_components` 시그니처가 다르면 같은 역할을 `rsa`+`sha2`(PKCS#1 v1.5 검증)로 직접 수행한다 — 결정(검증 라이브러리 사용, RS256만 허용, `kid` 선택)은 변하지 않는다.

### 토큰 갱신 위치 결정: 호스트(Rust)가 워커 실행 전에 갱신하고 짧은 수명의 access token만 환경변수로 넘긴다

근거:

1. refresh token은 **회전**한다(공식 문서: 갱신마다 새 refresh token, 같은 세션의 갱신은 직렬화). 저장소(`SecretStore`/설정 파일)·잠금·캐시는 호스트가 소유하므로 `tokio::sync::Mutex`로 직렬화하고 교체값을 즉시 영속할 수 있다. 워커는 단명 프로세스이고 저장소가 없어 회전된 토큰을 안전히 남길 수 없다.
2. 워커에는 만료 1시간짜리 access token만 간다. 30일짜리 refresh token은 호스트 밖으로 나가지 않는다(`env_clear` 스폰 계약, `process.rs:96`; 비밀은 임시 0600 파일이나 환경변수로만 전달하는 기존 관례, `refinement.rs:33-82,169`).
3. 창(WebView)은 어떤 토큰도 받지 않는다(완료 기준 2).
4. 키체인 질문 최소화: 읽기·쓰기 모두 "정제 직전·모델 목록 순간"에만, 갱신 때만 쓴다(`e283101`).

갱신 규칙: `now >= expires_at - 20분`이면 갱신(`ACCESS_TOKEN_REFRESH_MARGIN`, 도메인 상수). 스폰 시점에 최소 20분의 수명이 남으므로 일반적인 정제는 중간에 만료되지 않는다. 20분을 넘겨 401을 받으면 워커가 `CHATGPT_AUTH_REJECTED`로 끝내고, 호스트는 자동 재실행하지 않는다(다음 실행이 갱신한다). 갱신 실패 처리는 공식 문서를 그대로 따른다 — 사용 불가 코드(`invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated`, `refresh_token_reused`)는 토큰만 지우고(registration 유지) `signInRequired`로, 네트워크·5xx 같은 일시 오류는 아무것도 지우지 않고 `CHATGPT_REFRESH_UNAVAILABLE`로, `invalid_client`는 지우지 않고 `CHATGPT_CLIENT_INVALID`로 낸다. 응답의 `earliest_refresh_at`은 사용하지 않는다(공식 문서는 필드 존재만 적고 의미를 정의하지 않는다; "만료 근처에서 갱신"이라는 문서화된 지침만 따른다 — 실제 서버 반응은 수동 게이트 G11이 확인한다).

### 도메인 (`src-tauri/src/domain/chatgpt.rs` 신규, `domain/mod.rs` 등록; 프레임워크 금지, serde/thiserror/uuid만)

### 애플리케이션 (`application/`)

- `ports.rs` 추가 trait (모두 `Send + Sync`, `async_trait`):
  - `ChatGptAuthPort`: `sign_in(&SignInRequest, &mut oneshot::Receiver<()>) -> Result<SignInGrant, AppError>`, `refresh(&ChatGptRegistration, refresh_token) -> Result<ChatGptTokens, RefreshFailure>`, `revoke(&ChatGptRegistration, refresh_token) -> RevocationOutcome`, `list_models(access_token) -> Result<Vec<ChatGptModel>, AppError>`.
  - `ChatGptStore`: `load_settings`(비밀 미접촉), `save_preferences`, `load_or_create_host_id`, `load_registration`, `load_tokens`, `save_session(registration, Option<tokens>)`, `replace_tokens`, `clear_tokens`(registration 유지), `clear_session`(registration·tokens·모델 삭제, 모드 `ApiKey`, **host id 유지**).
  - `ChatGptEvents`: `emit(ChatGptSignInEvent)`.
  - `ClockPort`: `now_unix() -> u64`.
  - `RefinementJob`에 `transport: AssistantTransport` 필드 추가(`ports.rs:102-116`). `api_key`는 "베어러 자격 증명"으로 의미만 넓히고 타입·이름은 그대로 둔다 → `FakePort::refine`이 필드를 읽기만 하므로 기존 테스트 본문이 바뀌지 않는다.
- `application/chatgpt.rs` 신규 `ChatGptAccounts`(포트 4개 + `refresh_lock: tokio::sync::Mutex<()>` + 로그인 취소 슬롯): `settings()`, `save_preferences()`, `sign_in()`, `cancel_sign_in()`, `models()`, `sign_out()`, `access_for_refinement() -> ChatGptAccess { token, model }`. `models()`와 `access_for_refinement()`는 같은 비공개 헬퍼 `fresh_access_token()`을 공유한다(아래).
  - `sign_in`: 이미 진행 중이면 `CHATGPT_SIGN_IN_BUSY` → `load_or_create_host_id`(첫 로그인 전에 영속) → 저장된 registration(있으면 재로그인, `agent_name_hint` 생략, 콜백 `client_id` 생략 허용) 또는 신규(`dynamic_agent_client` + `agent_name_hint=Galpi`) → `auth.sign_in` → 재로그인이면 `grant.registration.subject == 저장된 subject` 확인(`CHATGPT_ACCOUNT_MISMATCH`) → `grant.tokens.grants_plan_usage()`가 거짓이면 registration만 `needs_consent=true`로 저장하고 `CHATGPT_PLAN_USE_NOT_GRANTED`(토큰은 저장하지 않으며 다음 로그인은 같은 `client_id`와 `prompt=consent`로 요청) → 참이면 `save_session`, 모델 기본값(서버 순서 첫 항목) 저장, 모드 `ChatGpt`로 전환.
  - `fresh_access_token() -> Result<(token, registration), AppError>`(비공개 공용 헬퍼): 토큰이 없으면 `CHATGPT_SIGN_IN_REQUIRED` → `refresh_lock`을 잡고 저장소에서 **다시 읽어** 만료를 판정(동시 호출 시 갱신 1회) → 필요 시 `auth.refresh` → `replace_tokens` → 잠금 해제 후 토큰 반환. 실패 분류는 위 "갱신 규칙". `models()`는 이 헬퍼로 얻은 토큰으로 `auth.list_models`를 호출하므로, 로그인 후 1시간이 지나 설정 시트를 열어도 만료 토큰으로 401을 받지 않는다. `access_for_refinement`: 모드가 `ChatGpt`일 때 헬퍼를 호출하고, 모델이 없으면 `CHATGPT_MODEL_REQUIRED`, 로그아웃·토큰 없음이면 `CHATGPT_SIGN_IN_REQUIRED`.
  - `sign_out`: 취소 슬롯 정리 → 토큰이 있으면 `auth.revoke`(서버 측 재시도는 어댑터) → 결과와 관계없이 `clear_session` → `{settings, remoteRevocationConfirmed}`.
- `use_cases.rs`: `Application`에 `chatgpt: ChatGptAccounts` 필드와 얇은 위임 메서드 6개를 더하고(`Application::new` 인자 하나 추가, `use_cases.rs:35-55`), `refine_transcript`(`use_cases.rs:119-180`)는 정제 슬롯을 잡기 전에 `settings().authMode`로 분기한다 — `ApiKey`는 기존 코드를 한 줄도 바꾸지 않고(`ASSISTANT_KEY_MISSING` 포함), `ChatGpt`는 `access_for_refinement()` 결과로 `RefinementJob { api_key에 access token, model: Some(slug), base_url: None, reasoning_effort: None, transport: Responses, .. }`를 만든다. 재시도 루프는 없다.

### 어댑터 (`adapters/outbound/`)

- `settings.rs` + 신규 `settings/chatgpt.rs`: `LocalSettingsStore`가 `ChatGptStore`를 구현. `Secret` 열거형에 `ChatGptTokens` 추가(`secrets.rs:22-37`; `secret()`/`store_secret()`/`secret_stored()`의 exhaustive `match` 3곳에 갈래 추가, `settings.rs:70-199`), `LocalSettings`(`settings.rs:219-247`)에 위 신규 키 추가하고 `is_empty()`에도 반영. `load_settings`는 `settings.json` 플래그만 읽는다(비밀 읽기 0회 — `InMemorySecrets.reads()`로 시험). `save_preferences`는 비밀을 건드리지 않는다.
- 신규 `chatgpt/` 디렉터리(모듈당 250 LOC 이하):
  - `mod.rs` — `ChatGptOAuthAdapter`(`ChatGptAuthPort` 구현; 필드: `reqwest::Client`(연결 10s·전체 30s), `OpenAiEndpoints`, `Arc<dyn BrowserOpener>`, `Arc<dyn ChatGptEvents>`, `Arc<dyn ClockPort>`, 폐기 정책). `OpenAiEndpoints::production()`은 `https://auth.openai.com/api/accounts/authorize`, `.../oauth/token`, `.../oauth/revoke`(discovery의 `revocation_endpoint`와 동일함을 확인), `https://auth.openai.com/.well-known/jwks.json`, issuer `https://auth.openai.com`, `https://api.openai.com/v1/models`. 테스트는 가짜 서버 URL로 교체한다. discovery를 매번 가져오지 않는 이유: 로그인·폐기마다 실패 지점이 하나 늘고, 공식 문서가 위 값들을 명시한다.
  - `pkce.rs` — `random_urlsafe(bytes)`(`getrandom` + base64url 무패딩), `code_challenge(verifier)`(S256). 검증자 64바이트, state·nonce 32바이트.
  - `loopback.rs` — `127.0.0.1`에 바인딩(먼저 `1455`, 사용 중이면 OS 할당 포트: 공식 문서가 첫 등록의 예시로 1455를 들고 이후 포트 변경을 허용하므로 둘 다 계약 안), `redirect_uri = http://127.0.0.1:<port>/auth/callback`. 접속마다 요청줄만 읽어(헤더 합계 8 KiB, 읽기 3초) `GET /auth/callback`만 처리하고 그 밖의 경로·메서드는 404/405, `Host`가 `127.0.0.1:<port>`가 아니면 400으로 거절한 채 계속 대기(브라우저의 투기적 연결·favicon이 대기를 막지 않게). 응답은 `Cache-Control: no-store`, `Connection: close`, 한국어 완료 페이지. 전체 대기 5분(`CHATGPT_SIGN_IN_TIMEOUT`), 취소 수신 시 즉시 종료.
  - `oauth.rs` — 인가 URL 조립(`client_id`, `redirect_uri`, `response_type=code`, `scope=openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, `resource=https://api.openai.com/v1`, `state`, `nonce`, `code_challenge`, `code_challenge_method=S256`, `ext_agent_host_id`; 신규 등록만 `agent_name_hint=Galpi`, 재로그인은 `login_hint=<저장 이메일>`, `needs_consent`면 `prompt=consent`), 콜백 판정(`state` 불일치 → `CHATGPT_STATE_MISMATCH`이며 코드 교환 없음, `error=access_denied`는 `state` 검증 뒤 `CHATGPT_CONSENT_DENIED`이며 교환 없음, 그 밖의 `error`는 `CHATGPT_SIGN_IN_FAILED`, 신규 등록 콜백에 `client_id`가 없거나 `dynamic_agent_client`면 `CHATGPT_REGISTRATION_INCOMPLETE`, 재로그인 콜백의 `client_id`가 저장값과 다르면 `CHATGPT_CLIENT_MISMATCH`), 코드 교환(form: `grant_type=authorization_code`, `client_id`, `code`, `code_verifier`, `redirect_uri`, `resource`), 갱신(form: `grant_type=refresh_token`, `client_id`, `refresh_token`, `resource`; `scope` 생략), 폐기(form: `token`, `token_type_hint=refresh_token`, `client_id`; 네트워크 오류·5xx는 정책(기본 3회, backoff 0.5s·1s; 테스트는 0)만큼 재시도 후 `Unconfirmed`, 로컬 삭제는 항상 진행). 오류 응답의 본문·`x-request-id`는 로그에 남기되 토큰·`code`는 남기지 않는다.
  - `id_token.rs` — JWKS GET → `kid`로 키 선택 → `jsonwebtoken` RS256 검증(issuer, audience=발급 `client_id`, `exp`, 5초 leeway) → `nonce` 일치, `sub` 비어 있지 않음, `email` 추출. 토큰 응답 `scope`에 `chatgpt.tokens.use.direct`가 있는지는 `ChatGptTokens::grants_plan_usage()`로 애플리케이션이 판정한다(어댑터는 granted scope를 있는 그대로 돌려줌).
  - `models.rs` — `GET /v1/models` + 베어러, `models[]`에서 `visibility == "list"`만 `{slug, display_name}`으로, **서버 순서 보존**.
  - `browser.rs` — `trait BrowserOpener { fn open(&self, url: &str) -> Result<(), AppError>; }`와 `TauriBrowser { app: AppHandle }`(`OpenerExt::opener().open_url`). 미확인 가정: Rust 직접 호출은 capability 범위 검사를 받지 않는다 → 구현 중 막히면 `capabilities/default.json`의 `opener:allow-open-url` allow에 `https://auth.openai.com/*`를 더한다(결정 변경 아님).
  - `SystemClock`(`ClockPort` 실제 구현)은 `chatgpt/mod.rs`에 둔다.
- `environment.rs`: `assistant_environment`에 `transport: AssistantTransport` 인자를 더해 `Responses`일 때만 `GALPI_ASSISTANT_TRANSPORT=responses`를 넣고 base URL·reasoning effort는 건너뛴다. `refinement.rs:129-135`의 호출부가 유일한 사용처다.
- `process.rs`: `ProcessResult`는 그대로 두고 `run_process` 안에서 `worker_protocol`일 때 `WorkerEvent::Error { code, message }`를 지역 변수에 기억해 두었다가, 종료 코드가 0이 아니고 `is_assistant_error_code(code)`이면 `AppError::new(code, message)`로 올린다(`process.rs:183-188`의 `PROCESS_FAILED` 앞). 전사·준비 오류의 기존 동작은 바뀌지 않는다(기존 테스트 `a_failing_child_reports_its_last_stderr_line`은 `worker_protocol: false`).

- `responses_stream.py` 신규(≤250 LOC, strict pyright): `build_responses_body(messages, model)` — `role == "system"` 메시지는 `\n\n`으로 이어 `instructions`로, 나머지는 `input: [{"role","content"}]`로, `store: false`, `stream: true`이며 `max_output_tokens`·`temperature`·`reasoning`·`previous_response_id` 등 preview 제한 목록의 필드는 보내지 않는다. `consume_responses_stream(lines, events, expected_chars, model, ..)` — `data:` JSON의 `type`으로 분기: `response.output_text.delta`는 본문 누적과 진행률(`streaming_percent` 재사용; 기존 `consume_assistant_stream`은 건드리지 않고 같은 스로틀 규칙을 새 함수가 따른다), `response.completed`만 성공, `response.failed`는 `response.error.code` 매핑, `response.incomplete`는 `CHATGPT_RESPONSE_INCOMPLETE`, `error` 이벤트와 스트림 중단(`response.completed` 없음)은 `CHATGPT_STREAM_INTERRUPTED`. `request_via_responses(...)` — `POST https://api.openai.com/v1/responses`, 헤더 `Authorization: Bearer`, `Content-Type: application/json`, `Accept: text/event-stream`, 명시적 `User-Agent: galpi-worker`(기본 `Python-urllib` UA가 일부 엣지에서 차단될 수 있어 고정; 실제 동작은 수동 게이트 G9가 확인), 타임아웃은 기존 `REQUEST_TIMEOUT_SECONDS` 재사용. - `refine.py::extract_chunk_notes`(맵 단계 병렬부, `refine.py:105-123`): 현재 `with ThreadPoolExecutor(..) as pool:` 안에서 `future.result()`가 첫 실패를 올려도 블록 종료 시 `shutdown(wait=True)`가 이미 제출된 대기 future를 모두 실행한다. 한도 초과(429)나 인증 실패 뒤에도 남은 청크 요청이 계속 나가 "재전송 없음"(완료 기준 7)이 깨진다. `cancel_futures=True`만으로는 이미 RUNNING 상태가 된 future를 막지 못하고(스레드가 이미 `extract()`에 들어간 뒤라 요청을 시작함) 실행 환경의 스케줄링에 결과가 좌우되므로, **공유 `threading.Event`(`failed`)** 로 막는다. `extract()`는 `request_minutes()`를 호출하기 직전에 `failed.is_set()`을 확인해 설정돼 있으면 요청 없이 반환(건너뜀)하고, `request_minutes()`가 예외를 올리면 `failed.set()` 후 재발생시킨다. 호출자는 `as_completed` 순회에서 첫 실제 예외를 올리며(건너뜀 결과는 예외가 아니므로 첫 실제 오류 코드가 유지된다), 올리기 전에 `pool.shutdown(wait=True, cancel_futures=True)`를 보조로 호출한다. 이미 요청이 진행 중인 청크(최대 `MAP_MAX_WORKERS`=3개)는 끝까지 기다린다. 이 변경은 전송 방식과 무관한 공유 코드라 API 키 모드에도 적용된다(하위 호환 절에 명시).
- `__main__.py`: `except AssistantError as error: events.fail(error.code, str(error)); return 1`를 일반 `Exception` 분기 앞에 추가(`__main__.py:89-96`).
- 한국어 메시지 표(워커 소유): 한도 초과 "ChatGPT 사용량 한도에 도달했습니다. ChatGPT 설정의 사용량에서 확인해 주세요. 앱은 요청을 다시 보내지 않습니다.", 사용량 확인 불가 "ChatGPT 사용량을 확인하지 못했습니다. 잠시 뒤 다시 실행해 주세요." 등 코드별 한 문장.

## 성능 영향

- **핫 패스 여부**: 아니다. 녹음 콜백·전사 파이프라인은 건드리지 않는다. 새 네트워크 호출은 로그인(1회), 정제 직전 갱신(만료 20분 전부터 ≤1회, 1회 HTTPS), 모델 목록(설정 시트를 ChatGPT 모드로 열 때 1회), 로그아웃 폐기(≤3회 시도)뿐이다.
- **복잡도 변화**: 정제 경로는 Rust에서 O(1) 호출이 추가되고, 워커 SSE 파서는 기존과 같은 선형 처리다. 설정 로드는 비밀을 읽지 않는 플래그 조회라 기존과 같다. 맵 단계 동시성(`MAP_MAX_WORKERS=3`, `minutes_pipeline.py:19`)은 그대로이며 ChatGPT 모드에서는 ChatGPT 5시간 사용량 한도를 더 빨리 소모할 수 있다(공식 문서 `profiles-and-sessions`).
- **빌드/배포 비용**: `reqwest`+`native-tls`+`jsonwebtoken(rust_crypto)`로 컴파일 시간과 바이너리 크기가 늘어난다. 측정 계획 — 변경 전후 `cargo build --release --manifest-path src-tauri/Cargo.toml`의 `target/release/galpi` 크기(`ls -l`)와 `cargo build --timings` 총 시간, `cargo tree --manifest-path src-tauri/Cargo.toml --prefix none | sort -u | wc -l`(전이 크레이트 수)를 PR 본문에 기록한다. 임계 기준은 두지 않고 증가량을 보고만 한다.
- **테스트 시간**: RS256 테스트 키 생성(2048비트)은 디버그 빌드에서 수 초가 걸릴 수 있어 `OnceLock`으로 테스트 바이너리당 1회만 만든다.

## 하위 호환성과 side effect

- **IPC 계약**: 기존 17개 커맨드의 이름·인자·반환은 불변이고 `AssistantSettings`(Rust `roster.rs:59-83`, TS `job.ts:28-37`, Zod `tauri-backend.ts:73-81`)도 불변. 추가분은 커맨드 6개(총 23개)·이벤트 `chatgpt-event` 1개이며, `docs/ARCHITECTURE.md` §2 표(현재 "14개")와 `AGENTS.md:49,69`("Sixteen"/"16", 실제 17개)의 낡은 숫자를 23개로 정정한다. 창과 호스트는 한 번들이라 버전 불일치는 없다.
- **워커 JSONL 프로토콜 v1**: 이벤트·필드 추가 없음, `error.code` 값 9개와 환경변수 `GALPI_ASSISTANT_TRANSPORT`만 추가. 환경변수가 없으면 기존 Chat Completions 경로를 타고 요청 본문·헤더는 같다. `refine` CLI 인자 불변. 안정 코드는 `process.rs`가 `AppError`로 올릴 때에만 쓰이고 전사·준비 오류 경로는 변하지 않는다. **단 하나의 API 키 모드 동작 변화**: `extract_chunk_notes`의 맵 단계에서 첫 실패가 기록된 뒤에는 새 청크 요청을 시작하지 않는다(이전에는 남은 청크를 모두 실행한 뒤 첫 예외를 올렸다). 이미 진행 중인 요청(최대 3개)은 끝까지 기다린다. 성공 경로·결과 파일·진행 이벤트는 같고, 실패 시 불필요한 제공자 호출과 비용이 줄어드는 방향의 변화다. 기존 테스트에 이 동작을 고정한 것은 없다(구현 단계에서 `unittest discover`로 확인).
- **저장 데이터**: `settings.json`에 신규 키만 추가되며 모두 `#[serde(default)]`다. `LocalSettings`에는 `deny_unknown_fields`가 없어(`settings.rs:219`) 이전 빌드로 내려가도 읽힌다. 단 이전 빌드가 설정을 한 번 저장하면 모르는 키(ChatGPT 로그인·host id)가 파일에서 사라져 재로그인이 필요하고 host id도 새로 생긴다. **Keychain 항목은 새로 만들지 않는다**(현재 `SettingsFile`; 레거시 `com.m16khb.galpi` 항목은 그대로). ChatGPT 토큰은 API 키·HF 토큰과 같은 0600 평문 파일 수준의 보호를 받으며 README에 같은 위험을 명시한다(이 계획이 약속을 낮추지 않는다 — 이미 `README.md:162-163`이 공개한 정책이다).
- **산출물 이름**: `_회의록.md` 규칙은 `domain/artifact.rs:40-47`의 `minutes_path` 그대로이고 `.aligned.v2.json`·`.srt`·`_화자별.txt`는 건드리지 않는다.
- **롤백 경로**: 커밋 되돌리기만으로 충분하다. 되돌린 빌드는 `chatgpt*` 키를 무시해 API 키 모드로 동작한다. 남는 로컬 refresh token(최대 30일 유효)은 사용자가 ChatGPT 설정의 연결된 앱에서 앱을 해제하면 무효가 된다 — 릴리스 노트에 적는다. 기능 스위치는 두지 않는다(모드가 `apiKey`인 한 신규 코드는 호출되지 않음).
- **개인정보**: ChatGPT 모드에서도 전사문·참석자·단어집·사전 정보가 외부(OpenAI)로 나간다는 `README.md:126` 경고를 ChatGPT 모드 설명에 맞게 갱신한다.

## 위험과 열린 질문

**열린 질문: 0개.** 아래는 모두 결정과 근거가 정해진 위험이다.

- **R1. 토큰 저장 강도**: 현재 `SecretStore`는 0600 평문 설정 파일이다. ChatGPT refresh token(30일, 회전)이 같은 수준으로 저장되므로 파일이 유출되면 30일간 계정의 ChatGPT 요금제를 쓸 수 있다. 결정: 기존 정책을 바꾸지 않고(Keychain 보류 사유는 `e283101`) 같은 `SecretStore` 경로에 얹으며 README에 위험을 명시하고 로그아웃 때 서버 측 폐기를 시도한다. Developer ID 서명 후 `LocalSettingsStore::new`의 한 줄 교체로 Keychain으로 넘어가며, 그때 갱신마다 쓰기가 생겨 질문 빈도는 "갱신 시점 1회"로 제한된다(읽기·쓰기를 시트·autosave에서 분리한 이번 설계가 전제).
- **R2. 공식 문서와 이슈의 로그아웃 차이**: 이슈를 따라 `client_id`를 지우므로 로그아웃 뒤 재로그인마다 새 동적 등록이 생겨 사용자의 ChatGPT 설정에 앱 항목이 쌓일 수 있다. 결정: 이슈 완료 기준 6을 우선한다. PR 본문에 차이를 명시해 리뷰에서 바꾸기로 하면 `clear_session`이 registration을 남기도록 한 곳만 고치면 된다(저장 구조는 이미 registration과 토큰이 분리돼 있다).
- **R3. 미확인 가정 — 첫 등록의 포트**: 공식 문서는 초기 등록부터 loopback을 요구하되 포트는 가변이라고 하며 1455는 "예시"다. 결정: 1455를 먼저 시도하고 사용 중이면 OS 할당 포트를 쓴다. 실계정 G3에서 두 경로를 모두 확인(1455를 다른 프로세스가 점유한 상태로 한 번 더 시도)한다.
- **R4. 미확인 가정 — `earliest_refresh_at` 의미**: 사용하지 않는다. 서버가 너무 이른 갱신을 거부하면 `Transient` 또는 사용 불가 코드로 분류돼 사용자에게 재로그인 안내가 나올 수 있다. 갱신은 만료 20분 전부터만 시도하므로 가능성은 낮고, G11에서 확인한다.
- **R5. 미확인 가정 — `Python-urllib` User-Agent·`api.openai.com` 응답**: 명시적 `User-Agent: galpi-worker`를 보내고 G9에서 실제 통과를 확인한다. 막히면 UA 문자열만 바꾼다.
- **R6. 정제 중 access token 만료**: 20분 마진으로 일반 회의는 안전하다. 초과 시 `CHATGPT_AUTH_REJECTED`로 끝나고 자동 재실행하지 않는다(재전송 금지 원칙). 사용자가 다시 실행하면 갱신된다.
- **R7. 사용량 한도**: ChatGPT Plus의 5시간 한도는 모든 앱이 공유한다. 맵 단계 3병렬이 한도를 빨리 쓸 수 있다. 결정: 병렬 수는 바꾸지 않고(이슈 범위 밖) 한도 오류 때 "사용량 관리" 링크로 안내하며 재전송하지 않는다.
- **R8. 의존성·빌드**: `reqwest` `native-tls`·`jsonwebtoken`의 feature·API 이름이 계획과 다르면 구현 첫 단계에서 `cargo check`로 확인해 같은 역할의 대안(`rsa`+`sha2` 직접 검증)을 쓴다. 결정 자체(Security.framework TLS, RS256 검증, 직접 의존성 최소화)는 유지한다. 모든 코드는 `clippy::pedantic`(경고 → `-D warnings`에서 오류), `unwrap_used`/`expect_used`/`panic` 거부 규칙을 지켜야 한다(`Cargo.toml:37-49`).
- **R9. 문서 파일 길이 제한**: `.issueops/documentation/manifest.json`의 모듈당 250줄 상한 때문에 ADR·CAUTIONS는 `project_docs_append`로 새 파일 1개씩 추가한다(루트 인덱스는 건드리지 않음).
- **R10. 설정 시트 접근성·시각 검증**: DOM 텍스트 검사는 픽셀 가시성이 아니다(캐션 `dom-visibility…`). 새 패널의 `hidden` 전환과 로그인 대기 중 취소 버튼은 번들 앱에서 눈으로 한 번 확인한다(G3·G15에 포함).
